# 將可平行任務成批整合、測試與審查，失敗時自動診斷並限定修正範圍

## 目標與啟用範圍

將「每個任務交付後各跑一次完整測試」改成「同批任務交付後，整合成固定版本，跑一次完整測試，再交給 reviewer」。

採用使用者選定的方向：

- 自動診斷與修正；證據不足、環境缺失或規格矛盾時才交給使用者。
- 新核准的 plan 預設使用批次流程；已核准的 plan 保持原流程。
- 第一版支援 pytest 與 tdd-crap。其他測試指令、明確略過測試的專案保留原流程，畫面顯示原因。
- 每個 writer 開發時仍跑相關測試；批次成功時只跑一次完整測試。基準測試、診斷及修正後重測另計，不宣稱整份 plan 永遠只測一次。

## 共同執行契約

### 成批與依賴

- 每份 plan 同時只有一個未結束批次，不跨 plan 混批。
- 建批時，依任務編號取前置全部完成的排隊任務，最多取核准時的 maxParallel 數量；固定成員及共同起始 commit，之後不追加任務。
- 席位不足時成員依序啟動，仍受全域 writer 上限限制。
- 下一批只能使用已接受的成果，不能把「已交付」當作前置完成。
- 成員明確卡住或逾時後，已交付成員可拆成新批次驗證；原批次記錄拆分去向，卡住者維持待處理。尚在正常執行的成員沿用現有逾時限制，不任意拆出。
- 有人放棄任務時依既有依賴規則處理，畫面列明放棄項目，不把它標成完成。

### 候選版本與接受成果

- 成員各自在獨立 worktree 實作。Alfred 依任務編號將交付 commit 整合至候選分支，不提前改動已接受的 plan 分支。
- Git 衝突交給一個整合 writer 處理；無法同時滿足需求時回報規格矛盾。
- 每次候選版本記錄批次 ID、修訂次數、起始 commit、成員 commit、候選 commit，以及測試指令與環境識別。
- 測試與審查必須對應同一候選 commit。任何程式、測試或合併解法變更，都使舊結果失效。
- 接受前再次核對 plan 分支起點；若被外部修改，重新建構、測試與審查。接受時使用原本驗證過的候選 commit，不另造未測過的合併版本。
- 一筆批次接受事件，同時確認該批成果與成員完成狀態；中斷後可補記，不重複合併。

### 測試門檻

- 第一批以 plan 起始版本為基準；後續批次使用上一個已接受版本的完整測試報告。
- pytest 與 tdd-crap 共用結構化 pytest 報告，記錄收集結果、各測試結果、跳過項目與原因；tdd-crap 另保留品質門檻結果。
- 保留 P0013 的 pytest／品質失敗分開比較規則。只有既有失敗時顯示「無新增失敗」，不顯示全部通過。
- 無法比較、報告缺失、收集失敗、超時、零測試、全部跳過或新增跳過項目，一律不能自動接受；顯示未完成驗證的原因。第一版不提供強制標成通過的操作。
- 基準與候選版本需使用相同測試指令、Python 環境及套件版本識別；不匹配時重建基準。P0010 的舊快取缺少所需報告資料時不可沿用。
- 必須保留每次完整輸出與報告；巢狀 pytest 子程序不得覆寫主測試報告，測試環境設定不得污染父程序。
- 基準、候選測試與診斷重跑都計入 P0012 的測試名額。

### 診斷與修正

- 新增測試失敗時，先在同一候選版本重跑一次失敗的 pytest 測試，確認能否重現；只有品質超標時直接分析品質報告。
- 唯讀診斷 agent 使用 reviewer 席位，取得需求、共同契約、任務改動對應、完整報告與重現結果。
- 診斷輸出限定為：單一任務修正、整合修正、環境問題或無法判定，並附需求編號、涉及任務、檔案位置及證據。
- 明確涉及一份任務時，只派一個 writer 修正該範圍；涉及多份或共同介面時，派一個整合 writer 修正。其他成員成果保留。
- 修正 writer 從失敗候選版本建立修正 worktree，能重現完整問題；不得回到缺少其他成果的舊分支盲修。Alfred 記錄修正與原任務的對應。
- 不自動窮舉移除任務的組合，也不將「移除 A 後通過」視為 A 有錯的充分證據。
- 測試失敗與審查退回共用每批最多三次自動修正額度；每次修正後重建候選版本、重跑完整測試並重新審查。
- 無法重現、環境問題、證據不足、規格矛盾或修正額度用完時，進入批次「等你處理」，不扣未涉及問題任務的個別重試額度。

### 整合審查與恢復

- 測試符合門檻後，審查整批成果；不再額外對每個成員各送一次相同用途的審查。
- reviewer 取得完整 plan 快照、共同契約、成員對照、候選版本及測試報告。一般批次驗證本批需求與跨任務一致性；最後一批另確認整份 plan 的非放棄需求皆已達成。
- 大型 diff 分段審查，最後彙整跨檔案結論；所有區段完成且無必改才可接受，不以截斷內容代替完整審查。
- 批次狀態、工作啟動及結果均可從事件重建。停止、放棄、額度不足及重啟沿用既有程序樹管理規則。
- 使用者可針對批次「重試並附說明」；不提供繞過測試與審查的「直接完成」。

## 介面與驗收

- 核准事件增加執行模式、選擇原因及規格快照；缺少新欄位的歷史事件一律視為逐任務模式。
- 狀態與 API 增加批次集合，包含成員、修訂、候選 commit、進度與待處理原因；保留現有 tasks、plans 的讀取相容性。
- 新增使用者專屬的 `board.py batch-retry PLAN BATCH --note 說明`，以及對應的批次重試 API；無強制完成選項。
- 新增模組使用 board_ 前綴，確認隨現有 runtime 打包機制交付。

端到端至少驗證：

1. A、B、C 各交付一次，僅跑一次候選完整測試，審查通過才一起完成。
2. A 是 B 的前置時分成兩批，B 取得已接受的 A。
3. C 卡住時可驗證 A、B，C 與整份 plan 不會被假標完成。
4. A 單一問題、A＋B 整合問題、環境問題與無法重現，分別走正確路徑。
5. 修正、審查退回、測試設定變更或外部 Git 改動，都使不適用的舊證據失效。
6. 停止、放棄、額度不足及各階段重啟，不重複測試、合併或標記完成。
7. 報告缺失、零測試、新增跳過、基準既有失敗及品質門檻超標，皆不被誤報為全部通過。
8. 執行完整 pytest 回歸；已知基準失敗須列明，新增失敗不得放行。啟用 TDD 時執行設定的品質檢查，不降低門檻。

## 前置與實作限制

- P0011、P0010、P0012 應先完成並合併，再核准 P0015；不可與會修改相同流程的 plan 同時實作。
- P0015 本身使用核准當時的既有流程，不在實作途中切換自己的執行模式。
- P0014 在 P0015 合併後再核准；核准前重新盤點函式與品質數字，避免依過時清單修整。
- 第一版不做任意任務組合搜尋、不承諾準確判定唯一責任任務、不自動改寫規格，也不自動合併或推送 main。
