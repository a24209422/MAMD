## 交付流程與範圍

- 本計畫承接對話已確認的使用方式。來源電腦仍需明確執行 export-state 並將輸出 commit、push；「後續 pull 自動更新」指目的電腦不需再跑 init 或手動 import，不代表 Git 自動提交尚未匯出的本機事件。
- 第一次將既有專案升級至此功能時，須由更新後的 MAMD 初始化目標專案，將 runtime、skills 與規則更新納入該專案。之後新的 clone 可由已交付的入口執行 init；若日後工具版本或環境設定有變，再按既有流程更新初始化。
- 第一版以單一開發者、一次一台電腦執行 Alfred 的交接為前提；不新增雲端資料庫、遠端常駐服務、Git hook 或兩台機器的分散式執行鎖。跨電腦不依賴絕對路徑，也不以 Git remote URL 當唯一專案識別；同一專案更換 remote 不應被誤判為另一專案。
- plan 的持久狀態與任務成果保持一致；活程序及外機執行中的任務不假裝在新電腦持續運作。來源停止後產生的排隊或待處理狀態依實際交接紀錄呈現，外機殘留的執行態以等待接續呈現，不改寫既有完成紀錄。
- schema 採明確的欄位白名單。審查與測試僅保留狀態接續所需的結構化結論及簡要原因，不包含原始日誌、測試命令、完整 stdout、認證資料或本機設定；這次不追求跨電腦完整還原 agent 對話紀錄及原始日誌查閱。
- 交接檔只由主專案的同步入口產生，不由任務 worktree 的 writer 更新；須驗證既有 commitAll、任務合併及 plan 合併不會把舊副本當新交接覆寫。發現不符 lineage 的版本時採 T2／T6 的分歧流程。
- 任務按 T1 → T2 → T3 → T4 → T5 → T6 → T7 執行；後續任務修改 board_core.py、board.py、conductor.py、board_setup、API、前端或共用測試時，都以前置任務的完成版本為基礎。本回合只撰寫並送出 plan，不直接實作，也不手動修改 .board。
